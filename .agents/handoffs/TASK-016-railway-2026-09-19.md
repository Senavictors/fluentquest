# Handoff — TASK-016

Última ferramenta: Codex desktop + Railway docs/plugin (somente leitura)
Última atualização: 2026-09-19

## Objetivo

Preparar o FluentQuest para iniciar com banco vazio e ser publicado no Railway, mantendo IA desligada, gravações persistentes e conta única do proprietário.

## Estado atual

As mudanças locais estão implementadas e o `npm run typecheck` e `npm run build` passaram. O Railway IaC foi carregado localmente e retornou os recursos esperados (Postgres, volume e app). O servidor `npm run dev:web` está ativo em `http://127.0.0.1:3215`; sem `.env.local`/PostgreSQL, `GET /api/bootstrap` falha e a tela local não conclui o carregamento.

Nenhum recurso foi criado no Railway e nada foi enviado ao GitHub. A configuração aponta para `Senavictors/FluentQuest` em `main`, mas ainda precisa estar no remoto antes de conectar e implantar. A conta Railway listada nesta sessão contém `PhisioFlow`; não usar esse projeto. O app precisa ser vinculado a um projeto dedicado.

## Concluído

- Scripts de start, migração e criação do proprietário sem `.env.local` para Railway.
- Criação do proprietário agora aceita as variáveis do container e mantém `.env.owner` como fallback local.
- Validação de `BETTER_AUTH_SECRET` em produção (mínimo 32 caracteres); a imagem usa um placeholder somente na etapa de build.
- `Dockerfile`, `.dockerignore` e `.railway/railway.ts`: serviço de app único para web+worker, Postgres gerenciado vazio, volume de 1 GiB em `/app/data`, IA desligada, sem domínio público na IaC.
- ADR-007, TASK-016, contexto e documentação de deploy atualizados.
- Typecheck, build Next.js e `git diff --check` concluídos. A avaliação local do IaC listou somente `fluentquest-postgres`, `fluentquest-files` e `fluentquest-app`.

## Em andamento

- TASK-016 está na pasta `active/`; os critérios da preparação estão marcados como concluídos. A publicação real fica para a continuação após escolher/vincular um projeto Railway dedicado.
- A aba local continua servindo frontend, mas não é funcional sem banco e credenciais.

## Próximos passos

1. Revisar `git status` e publicar as alterações no GitHub quando o proprietário pedir.
2. Instalar/atualizar a Railway CLI, criar projeto vazio dedicado e vinculá-lo; não selecionar `PhisioFlow`.
3. Executar `railway config plan` e conferir que só serão adicionados app, Postgres e volume e que nada será removido.
4. Com autorização para aplicar, criar os recursos, configurar um `BETTER_AUTH_SECRET` forte no serviço e esperar as migrações.
5. Criar uma única conta por SSH com `npm run owner:create:railway` e variáveis lidas sem ficarem no histórico.
6. Só quando for adequado publicar, gerar domínio Railway, definir `BETTER_AUTH_URL` com a URL HTTPS exata e redeployar.
7. Configurar backups separados para PostgreSQL e volume.

## Falhas atuais

- Ambiente local: `.env.local` e PostgreSQL local ausentes; chamadas de bootstrap ao banco respondem 500.
- Docker: engine do Docker Desktop não está ativo.
- Railway: somente projeto `PhisioFlow` apareceu na conta; nenhuma criação/deploy foi feita.
- A skill `bootstrap-audit` e os comandos/arquivos `bootstrap-audit`/`bootstrap-handoff` não foram encontrados nas skills ou arquivos locais. Foi feita revisão manual e `git diff --check`; nenhum commit foi criado.

## Decisões tomadas

- Banco Railway novo e vazio, sem tentativa de recuperar dumps inexistentes.
- Web e worker no mesmo serviço/volume e uma réplica, para armazenamento local dos arquivos.
- IA desligada e domínio não declarado até a publicação ser escolhida.
- `BETTER_AUTH_SECRET` persistente e `BETTER_AUTH_URL` igual à origem HTTPS pública.

## Não refazer

- Não repetir typecheck/build sem mudanças de código.
- Não procurar o banco antigo ou configurar o projeto `PhisioFlow`.
- Não importar o pacote de mockups do Drive: ele contém apenas mockups e não credenciais.
